= Publish to the program-forge registry
:toc: left
:icons: font

How to get the built conda packages into the project's MinIO-backed conda registry, and how to consume them afterwards.

[source,console]
----
pixi run conda                              # build them first
pixi run publish --dry-run                    # check what would go out
pixi run publish                              # upload and index
----

== Before you start

Build the packages.
Publishing never builds, so that a publish cannot quietly ship something other than what you tested:

[source,console]
----
pixi run conda
----

Only packages matching the version in `Cargo.toml` are published.
`build/conda` accumulates — a version or variant change alters the filename — so a run refuses to proceed if any distribution is missing at the current version, rather than publishing a half-set.

== Provide credentials

Credentials are never passed as command-line arguments, where they would land in shell history and in the process list.
Use any one of these; the task reports which it found:

[source,console]
----
export S3_ACCESS_KEY_ID=...
export S3_SECRET_ACCESS_KEY=...
----

`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` work too, as does an `s3://` entry in `~/.rattler/credentials.json`, which is the more idiomatic place for a pixi setup:

[source,json]
----
{
  "s3://program-forge": {
    "S3Credentials": {
      "access_key_id": "...",
      "secret_access_key": "..."
    }
  }
}
----

If none of the three is present the task stops before contacting anything and lists the options.
`--dry-run` works without credentials.

== Check first

[source,console]
----
pixi run publish --dry-run
----

[source,text]
----
package:  mq-bridge-ros2 0.4.19
registry: http://127.0.0.1:19000
          from [s3-options.program-forge] in config.toml
channel:  s3://program-forge
publishing 2 package(s):
  build/conda/linux-64/mq-bridge-ros2-0.4.19-ros2_humble_hee40719_0.conda
  build/conda/linux-64/mq-bridge-ros2-0.4.19-ros2_jazzy_h2a6e838_0.conda

dry run, nothing contacted. The commands would be:

  rattler-build upload s3 --channel s3://program-forge ...
  rattler-index s3 s3://program-forge ...
----

Nothing is contacted, so this is safe to run against a registry you are not sure about.

== Publish

[source,console]
----
pixi run publish
----

The channel then holds, per platform subdirectory, the packages and a regenerated index:

[source,text]
----
linux-64/mq-bridge-ros2-0.4.19-ros2_humble_hee40719_0.conda
linux-64/mq-bridge-ros2-0.4.19-ros2_jazzy_h2a6e838_0.conda
linux-64/repodata.json
linux-64/repodata.json.zst
linux-64/repodata_shards.msgpack.zst
noarch/repodata.json
----

== Why publishing is two steps

Uploading is not publishing.
A conda channel *is* its `repodata.json`: a client reads that file to learn what exists, and never lists the bucket.
Packages uploaded without a regenerated index are invisible — present, paid for in storage, and unusable.

`rattler-build upload` does not index, so the task runs `rattler-index s3` afterwards.

`--no-index` skips it, which is only useful when publishing several projects in a row and indexing once at the end.
The task says plainly that it left the channel unpublished:

[source,console]
----
pixi run publish --no-index
----

== Re-publishing the same version

The upload refuses to overwrite:

[source,text]
----
Error: × Package s3://program-forge/linux-64/mq-bridge-ros2-0.4.19-ros2_jazzy_h2a6e838_0.conda
  │ already exists. Use --force to overwrite.
----

That is a feature — a published version should be immutable, and the usual right answer is to track the next `mq-bridge` release:

[source,console]
----
pixi run follow-version && pixi run conda && pixi run publish
----

Use `--force` only when replacing a package nobody has installed yet:

[source,console]
----
pixi run publish --force
----

== Consume the channel

A consumer names the registry's *canonical identity*, never the `s3://` URL this task writes to:

[source,toml]
----
[workspace]
channels = [
    "https://program-forge.invalid",
    "https://prefix.dev/robostack-jazzy",
    "conda-forge",
]

[dependencies]
mq-bridge-ros2 = "*"
----

Because the ROS distribution is in the build string, ask for the one you want explicitly when both are published:

[source,toml]
----
mq-bridge-ros2 = { version = "*", build = "ros2_jazzy_*" }
----

=== Why the channel is a name and not a location

`https://program-forge.invalid` can never resolve — `.invalid` is reserved by RFC 2606 — and that is deliberate.
It is an identity, and pixi's global configuration gives it a location:

[source,toml]
----
[mirrors]
"https://program-forge.invalid" = [
    "http://127.0.0.1:19000/program-forge",
    "https://nexus-dains-vu.isis.vanderbilt.edu/dains-conda",
]
----

Three consequences matter here.

A reader needs no S3 credentials::
The mirror is a plain HTTP URL, so pixi fetches the packages and `repodata.json` over HTTP.
Only *writing* needs the S3 API, which is why this task is the only thing that requires credentials.

A manifest survives the registry moving::
Nothing outside that `[mirrors]` block knows where the bytes live, so a project's channel list does not change when the registry does.

Naming the `s3://` URL directly would bypass all of it::
It would require every consumer to hold S3 credentials, and pin them to one location.

`publish.py` reads the endpoint out of that same configuration rather than repeating it, so the location has one spelling.
Verify the whole path end to end with the canonical name:

[source,console]
----
pixi search -c https://program-forge.invalid mq-bridge-ros2 --platform linux-64
----

== Point it at another registry

Every part of the target is overridable, by flag or by environment variable:

[cols="2,2,3", options="header"]
|===
| Flag | Environment | Default

| `--channel`
| `S3_CHANNEL`
| `s3://<bucket>`, from pixi's `[s3-options]` or `[mirrors]`

| `--endpoint-url`
| `S3_ENDPOINT_URL`
| from pixi's `[s3-options]`, falling back to `[mirrors]`

| `--region`
| `S3_REGION`
| `us-east-1`

| `--addressing-style`
| `S3_ADDRESSING_STYLE`
| `path`
|===

The first two are derived, not hardcoded.
`publish.py` reads them out of pixi's global configuration, preferring `[s3-options.<bucket>]`:

[source,toml]
----
[s3-options.program-forge]
endpoint-url = "http://127.0.0.1:19000"
region = "us-east-1"
force-path-style = true
----

That block states the S3 endpoint for a bucket outright, which is exactly the question a publish asks.
`[mirrors]` is the fallback, and only a fallback: it answers a *read* question, its entries are ordered by read preference, and its first entry could legitimately become a read-only remote while the local registry is down.
Deriving a write target from it is an inference; `[s3-options]` is a statement.
When both are present the two are cross-checked — the bucket the mirror addresses is the one looked up in `[s3-options]` — so they cannot drift apart unnoticed.

The task reports which source it used, so this is never guesswork.
Change either and publishing follows, with no second copy of the URL to update.
If neither is found the task stops and says so, rather than trying to write to a name that cannot resolve.

[NOTE]
====
Neither publishing tool reads that configuration itself.
`rattler-build upload s3` lists `--endpoint-url` and `--region` as required arguments and rejects the command without them even when handed `--config-file` containing exactly those values, and `rattler-index s3` has no `--config-file` at all.
Both honour the `S3_ENDPOINT_URL` and `S3_REGION` environment variables, which is how "required" is satisfiable without flags.
So `publish.py` reads the configuration and passes the values on.
====

The other two are about MinIO specifically.

`--addressing-style path`::
MinIO is addressed path-style — `endpoint/bucket/key`.
Virtual-host style, the S3 default, puts the bucket in the hostname and needs a wildcard DNS record per bucket, which a local deployment almost never has.

`--region us-east-1`::
MinIO ignores the region entirely, but the AWS SDK refuses to build a client without one.

For a genuinely different registry, override both:

[source,console]
----
pixi run publish --endpoint-url http://other-host:9000 --channel s3://other-bucket
----

== Try it against a throwaway registry

Worth doing before trusting a real one, and how the task itself was verified.
Start a MinIO, create the bucket, publish to it, and inspect the result:

[source,console]
----
MINIO_ROOT_USER=minioadmin MINIO_ROOT_PASSWORD=minioadmin \
  minio server /tmp/minio-data --address 127.0.0.1:9000 &

mc alias set forge http://127.0.0.1:9000 minioadmin minioadmin
mc mb forge/program-forge

S3_ACCESS_KEY_ID=minioadmin S3_SECRET_ACCESS_KEY=minioadmin \
  pixi run publish --endpoint-url http://127.0.0.1:9000

mc ls -r forge/program-forge/
mc cat forge/program-forge/linux-64/repodata.json
----

The repodata is the thing to check.
Both packages should be listed, with their ROS dependencies distribution-specific:

[source,text]
----
mq-bridge-ros2-0.4.19-ros2_humble_hee40719_0.conda
  depends=['python', 'ros-humble-ros-base', 'ros-humble-std-msgs', ...]
mq-bridge-ros2-0.4.19-ros2_jazzy_h2a6e838_0.conda
  depends=['python', 'ros-jazzy-ros-base', 'ros-jazzy-std-msgs', ...]
----

[WARNING]
====
Stop only the server you started.
`pkill -f "minio server"` will also kill any other MinIO on the machine, including the real registry if it runs locally.
Find the specific process first:

[source,console]
----
pgrep -af "minio server /tmp/minio-data"
kill <that pid>
----
====
