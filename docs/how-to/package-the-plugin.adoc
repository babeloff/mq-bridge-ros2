= Package the plugin for distribution
:toc: left
:icons: font

How to produce each of the four artifacts, and what each one is valid for.

[IMPORTANT]
====
Every artifact here is specific to one platform *and* one ROS distribution.
`rclrs` selects its `rcl` bindings at compile time and that ABI differs between distributions, so a `jazzy` build will not work on `humble`.
Plan on one artifact per platform per distribution, not one per platform.

The conda packages handle this properly, because a build string can say which distribution a package is for.
A Python wheel's platform tag cannot, which is the one place this leaks.
====

[NOTE]
====
Switching distribution is safe, but only because something takes care of it.

`rclrs`' build script reads `ROS_DISTRO` and `AMENT_PREFIX_PATH` yet declares no `cargo:rerun-if-env-changed` for either, so cargo does not treat a change of distribution as a reason to rerun it.
One shared target directory across distributions would link one distribution's bindings against another's libraries, and fail at load time rather than at build time.

Three things prevent that: the task scripts give each distribution its own subdirectory of whatever target directory cargo is configured to use, every rattler-build variant gets its own work directory, and the recipe pins `CARGO_TARGET_DIR` inside it.
Building by hand outside those paths still needs a target directory per distribution.
====

== Build the conda packages

These are the project's primary artifacts, built with https://rattler.build[rattler-build] from `recipes/recipe.yaml`.
One command builds every ROS distribution:

[source,console]
----
pixi run package
----

[source,text]
----
building for ROS 2: humble, jazzy

conda package(s):
  build/conda/linux-64/mq-bridge-ros2-0.1.0-ros2_humble_hee40719_0.conda
  build/conda/linux-64/mq-bridge-ros2-0.1.0-ros2_jazzy_h2a6e838_0.conda
----

The distribution is in the build string, so the two cannot be installed over each other by accident.
Each build also runs a test that imports the package and `dlopen`s the library, which catches a missing run dependency before a user does.

To build just one while iterating:

[source,console]
----
pixi run package --distro jazzy
----

=== Adding a distribution

The distributions are a *variant axis*, not a value in the recipe.
Add one to the `ros_distro` list in `recipes/variants.yaml` and that is the whole change:

[source,yaml]
----
ros_distro:
  - humble
  - jazzy
----

`package.py` reads that list to decide what to build and derives the channel for each one, so nothing else has to be kept in step.
Two conditions apply: `rclrs` must support the distribution — as of 0.7 that is `humble`, `jazzy`, `kilted` and `rolling` — and RoboStack must publish a `robostack-<distro>` channel for it.

=== Why each distribution is built separately

`package.py` runs rattler-build once per distribution, each with only that distribution's RoboStack channel, rather than expanding the variant axis in a single run.

That is not tidiness.
Most ROS conda packages are distribution-prefixed and would be unambiguous with several channels present, but `ros2-distro-mutex` is not: it exists in every RoboStack channel with a distribution-specific build string, and it is precisely what stops two distributions being mixed in one environment.
With two RoboStack channels and strict channel priority, the mutex resolves from whichever channel comes first, and every other distribution then fails to solve with a long complaint about `ros2-distro-mutex ... jazzy_*` being excluded.

One channel per invocation respects that guard rather than defeating it, and makes each build hermetic.

== Build the Python wheel

[source,console]
----
pixi run package --wheel
----

The builder is mq-bridge's, not this project's.
It compiles the `cdylib`, stages it next to `mq-bridge-plugin.json` inside `python/mq_bridge_ros2/`, and applies the platform tag.

Run it once per operating system and architecture you publish for, under the same distribution name; pip selects the right wheel by platform tag.

[WARNING]
====
A wheel's platform tag has no room to express the ROS distribution.
Nothing stops a user pip-installing a `jazzy`-built wheel on a `humble` machine, and it will fail at load time rather than at install time.
If you publish wheels for more than one distribution, they need separate distribution names or a separate index.
====

== Build the npm package

The npm release is a single package containing every platform's binary under `node/prebuilds/`.
Stage on each target:

[source,console]
----
mq-bridge-package-plugin
----

Then merge the resulting `node/prebuilds/` directories from every target onto one machine, and pack once:

[source,console]
----
mq-bridge-package-plugin --pack --out npm
----

== Build the standalone archive

For hosts that load a library by path and want nothing to do with pip or npm, the release workflow produces an archive of just the library and its manifest.
See the `Build standalone plugin archive` step in `.github/workflows/release.yml`; it names the archive after both the platform and the distribution.

== Keep the versions in step

`Cargo.toml` is the source of truth.
Both npm manifests, `python/pyproject.toml` and the conda recipe's `context.version` must agree with it, or a release ships mismatched versions:

[source,console]
----
pixi run bump-version minor    # choose a new version, write it everywhere
pixi run sync-version --check  # verify they agree
----

CI runs the check, and `pixi run check` includes it.

== Release from CI

Pushing a numeric tag runs `.github/workflows/release.yml`, which builds for four targets — `linux-x64-gnu`, `linux-arm64-gnu`, `darwin-x64` and `darwin-arm64` — and publishes the crate, the npm package and the wheels.

`pixi run release` is the front door: it checks the tree, the branch, the tag, CI, `check` and the test suites in every environment before creating the tag, and pushes only when asked.
See xref:../reference/pixi-tasks.adoc[Pixi tasks].

ROS, the Rust toolchain and python all come from the locked pixi environment, installed with `locked: true` rather than re-solved on each runner.
That is what keeps a release off the failure mode that broke CI: a fresh solve validates each download against the size recorded in the channel's repodata, and that metadata is not always right, whereas the lock records a sha256.
It also means one interpreter does everything, which is why `pip` is a pixi dependency — the packaging tools are pip-installed into that environment.

The distribution it targets is the workflow-level `ROS_DISTRO_TARGET`, paired with `PIXI_ENVIRONMENT`, the environment that provides it.
Releasing for a second distribution means running the workflow again with different values — deliberately not a matrix axis, because the wheel filenames would collide.

[NOTE]
====
mq-bridge's packaging tools look for the compiled library at `<root>/target/release/` literally.
They honour neither `CARGO_TARGET_DIR` nor a `build.target-dir` set in a cargo configuration file, so on a machine that points target-dir at a shared cache — a common setting — cargo succeeds and the packager then reports `cargo produced no shared plugin library`.

`pixi run package --wheel` pins the variable to what the packager expects, and the release job sets it too.
Building by hand outside those paths needs the same.
====

== Windows is not built

`win32-x64-msvc` is absent from the release matrix.

The pixi environment installs on Windows without complaint — that step succeeded
on a real runner — and so does the pip install of the packaging tools.
What fails is linking the `cdylib`:

[source,text]
----
error LNK2019: unresolved external symbol
  __imp_test_msgs__msg__ComplexNestedKey__Sequence__fini
...
mq_bridge_ros2.dll : fatal error LNK1120: 21 unresolved externals
----

Every missing symbol comes from `test_msgs`, the package `rclrs` vendors and
links unconditionally whether or not a route uses it — the same dependency that
has to be installed everywhere else for the crate to link at all.
The `__imp_` prefix means MSVC is looking for a DLL *import library* for those
symbols.

=== What this costs

No Windows binary is published, so:

* the npm package carries no `win32-x64-msvc` prebuild, and `register()` on
  Windows raises the loader's "no prebuild for this platform" error;
* no Windows wheel is published, so `pip install mq-bridge-ros2` there finds
  nothing to install.

Nothing else is affected. Linux and macOS are unchanged, and the conda packages
are built separately from this matrix.

=== Restoring it

`win-64` is still a declared platform in `pixi.toml`, and `pixi.lock` still
covers it, so the environment side needs no work — restoring the build is
re-adding the commented matrix entry in `release.yml`.

Before doing that, establish which of two causes it is. Both are cheap to check
by adding a step to the Windows job:

Missing import libraries::
Look for `test_msgs__rosidl_generator_c.lib` and its siblings under the
environment's `Library/lib`. If they are not shipped, RoboStack's Windows
packages cannot satisfy the link and the fix has to come from upstream.

The linker cannot see them::
If the `.lib` files are present, print `LIB` in the job. `rclrs`' build script
emits link directives but relies on the environment to put the library directory
on the linker's search path, and that is exactly the kind of thing that differs
between an activated conda shell and pixi's own activation.

Only the second is fixable here — by exporting `LIB` in the job, or by passing
the directory through `RUSTFLAGS`.

== The licence has to reach four places

`LICENSE` at the repository root is not enough on its own, because each packaging tool looks somewhere different:

[cols="1,3", options="header"]
|===
| Artifact | How the licence gets in

| crate
| `Cargo.toml`'s `include` list. An explicit `include` overrides cargo's defaults, so `/LICENSE` has to be listed or the published crate carries none.

| conda
| `about.license_file` in `recipes/recipe.yaml`, which puts the text in the package's `info/licenses/`.

| npm
| `node/LICENSE`. npm always includes a licence regardless of the `files` array, but it packs from `node/` and does not look above it.

| wheel
| `python/LICENSE`. setuptools discovers `LICEN[CS]E*` next to `pyproject.toml`, and lands it in `dist-info/licenses/`.
|===

The last two are copies of the root file.
That duplication is only safe if the copies cannot drift, so `pixi run check` compares them and fails if they differ.

== A build dependency that is easy to miss

`rclrs` vendors the generated code for several message packages and links their libraries unconditionally, whether or not a route uses them.
`ros-<distro>-test-msgs` and `ros-<distro>-example-interfaces` are therefore *required* build dependencies.
Without them the crate does not link, with a long list of `cannot find -ltest_msgs__rosidl_generator_c` errors.

Both are listed in `recipes/recipe.yaml`, `pixi.toml` and the CI workflows for this reason.
